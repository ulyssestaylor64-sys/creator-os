# Creator OS 技术审计与开源整合方案

> 审计日期：2026-10-23
> 审计对象：`ulyssestaylor64-sys/creator-os`（线上：https://creator-os-yaf6.onrender.com）
> 开源仓库核查方式：GitHub API 读取仓库元数据、README、依赖清单与目录结构（非逐行阅读全部源码）

---

## 0. 结论摘要

1. **不建议替换现有技术栈。** 当前「FastAPI + 单页静态前端」结构轻、部署简单，改造成本低，替换成 Postiz / PostSider 这类 Next.js 单体会带来数据库、Redis、Node 运行时和 AGPL 义务，收益不值。
2. **Easel 是本项目最值得复用的仓库**（Python、Apache-2.0、4027 stars、当天仍在更新），适合复用它的**技能定义、提示词结构、媒体处理脚本**，而不是整包引入（依赖极重：Playwright、faster-whisper、OpenCV、rembg）。
3. **Postiz / PostSider 只适合作为「独立发布服务」通过 API 调用**，不建议合并进本仓库：两者均为 AGPL-3.0、TypeScript 单体、依赖 Postgres/Redis。
4. **Content Pilot 不建议接入**：MIT 许可没问题，但项目停更约 8 个月、仅 11 stars，且发布依赖 Playwright 保存 Cookie 登录，存在平台合规与账号安全风险，只适合参考 UI 与任务模型。
5. **本轮已修复一个影响真实使用的数据一致性 Bug**（选题/爆款的列表与详情对不上），并已验证通过。

## 1. 现有项目审计

### 1.1 技术架构

| 层 | 现状 |
|---|---|
| 前端 | `index.html` + `assets/style.css` + `assets/app.js` + `assets/charts.js`，原生 JS 单页，6 个页面用 `data-page` 切换；ECharts 本地引入；字体与图表库来自 `_shared/` |
| 后端 | FastAPI（`server.py` + `api/routes.py`），14 个接口，全部返回 JSON |
| 数据 | 无数据库。`api/mock_data.py` 现场生成演示数据；用户操作仅存在浏览器 localStorage |
| AI | `api/ai_client.py` 调用智谱 GLM，已接入「AI 初稿」；无 Key 或调用失败自动回退 mock |
| 部署 | Render（`render.yaml`，免费计划），GitHub 自动部署；GitHub Pages 为纯静态旧版 |
| 安全 | 无登录、无鉴权、无速率限制；API Key 仅存 Render 环境变量 |

### 1.2 功能清单

| 模块 | 状态 | 实现方式 | 主要缺口 |
|---|---|---|---|
| 01 工作台总览 | ✅ 可用 | 前端静态数据 + ECharts | 指标不来自真实抖音账号，无数据同步 |

| 签到 / 积分 / 抽奖 | ✅ 可用 | 纯前端 localStorage | 无服务端校验，清缓存即重置 |
| 定价 / 帮助 / 搜索 | ✅ 可用 | 前端模态框 | 无真实支付与账号体系 |
| 多设备同步 | ❌ 未实现 | — | 需要账号体系 + 数据库 |

### 1.3 已发现并修复的问题（P0）

**选题与爆款的列表/详情错位。**

- 原因：`generate_topics()` / `generate_hits()` 每次请求用 `random` 重新生成 id 和文案；`generate_topic_detail()` 用 `id` 最后一位猜索引，导致点开第 1 条看到第 4 条的内容。
- 修复：改为固定数据池（`TOPIC_POOL`、`HIT_POOL`），id 与内容一一对应；趋势等数值用 `md5(id)` 作为种子，保证同一资源多次请求稳定。
- 附带修复：未知 id 返回 404 而非随机内容；导入的爆款写入进程内缓存，导入后可立即查看详情。
- 验证：列表与详情标题 100% 匹配；刷新前后 id 不变；未知 id → 404。

## 2. 开源项目核查

### 2.1 核查结果（GitHub API 实测）

| 项目 | Stars | 语言 | 许可证 | 最近推送 | 技术栈 | 结论 |
|---|---:|---|---|---|---|---|
| [ZJU-REAL/Easel](https://github.com/ZJU-REAL/Easel) | 4,027 | Python | Apache-2.0 | 2026-10-23 | FastAPI + Uvicorn + CLI，113 个技能，MCP/OpenClaw | **可复用模块** |
| [r04943083/content-pilot](https://github.com/r04943083/content-pilot) | 11 | Python | MIT | 2026-03-03 | NiceGUI + Playwright + Cron | **仅参考** |
| [gitroomhq/postiz-app](https://github.com/gitroomhq/postiz-app) | 37,615 | TypeScript | AGPL-3.0 | 2026-10-22 | Next.js 单体、Postgres、Redis、pnpm workspace | **外部服务调用** |
| [lumizone/postsider](https://github.com/lumizone/postsider) | 13 | TypeScript | AGPL-3.0 | 2026-10-13 | Docker、REST API、Node SDK、MCP，33 个连接器 | **外部服务调用** |

### 2.2 逐项判断

**Easel（最匹配）**

- 目录结构：`easel/`（CLI、gateway、发布器）、`web/`（FastAPI + Vite 前端）、`skills/builtin/`（`copywriting`、`card-xiaohongshu`、`auto-subtitle`、`ai-video-gen`、`asset-manager`、`image-editing` 等）、`docs/`（技能规范、提示词栈）。
- 可直接复用：
  - 技能定义与提示词模板（Apache-2.0，保留署名即可）；
  - 字幕、卡片图、视频合成等媒体脚本；
  - 平台发布适配层的接口设计思路。
- 不建议整包引入：依赖包含 `playwright`、`faster-whisper`、`opencv-python`、`rembg`、`librosa`、`biliup`，镜像体积与构建时间会翻数倍，Render 免费实例扛不住。
- 接入成本：中。建议以「独立 sidecar 服务」方式按需部署，主站只调用少量 HTTP 接口。

**Content Pilot（仅参考）**

- 优点：MIT、结构简单，有看板/日历/发布队列的完整产品思路，可借鉴数据模型。
- 风险：依赖 Playwright + Cookie 登录发布，属于绕过平台官方授权的方式；项目停更，无法保证选择器与登录流程长期有效。
- 结论：只借鉴「草稿状态机 + 发布队列 + 日历视图」，不引入代码。

**Postiz（外部服务）**

- 优点：多平台排期、日历、分析看板成熟，37k stars，持续维护。
- 约束：AGPL-3.0；Next.js 单体 + Postgres + Redis，自托管资源要求远高于当前 Render 免费实例；对本项目而言是「另一套系统」。
- 结论：如果要做真正的多平台发布，**单独部署 Postiz，通过它的 Public API 提交排期**，本仓库不复制其代码。若修改其源码并对公网提供服务，需按 AGPL 开源修改部分。

**PostSider（外部服务）**

- 优点：架构清晰（`apps/backend`、`apps/mcp`、`apps/sdk`），33 个连接器，REST API + MCP，适合作为「AI Agent 发布通道」。
- 约束：AGPL-3.0、Docker 自托管、项目很新（13 stars），连接器稳定性未经验证。
- 结论：与 Postiz 二选一，优先 Postiz（生态与维护更成熟）；PostSider 作为 MCP 场景的备选。

### 2.3 合规红线

- 抖音/小红书/B站 的自动发布，**必须走官方开放平台授权**（OAuth），不得使用账号密码、Cookie 注入或模拟登录绕过限制。
- 第三方数据（热榜、评论、竞品）没有免费官方接口，需采购巨量算数/新榜等服务，或由用户手动导入。
- 引入 AGPL 项目时，保持「独立进程 + 网络调用」边界，避免把其代码链接进本仓库。

## 3. 推荐整合方案

```
┌─────────────────────────────────────────────┐
│  Creator OS 前端（现有 SPA，不换框架）        │
└───────────────┬─────────────────────────────┘
                │ /api
┌───────────────▼─────────────────────────────┐
│  Creator OS 后端（现有 FastAPI）             │
│  ├─ 业务 API（现有 14 个）                   │
│  ├─ SQLite/Postgres（新增：用户数据持久化）   │
│  ├─ AI 适配层（GLM，现有）                   │
│  └─ 外部适配器（新增，可插拔）                │
│      ├─ 热榜适配器：官方/付费 API → 统一结构   │
│      ├─ 发布适配器：Postiz Public API         │
│      └─ 媒体适配器：Easel skills（可选 sidecar）│
└─────────────────────────────────────────────┘
```

原则：**主站保持单体轻量，外部能力一律通过适配器调用**。每个适配器都可关闭，关闭时回退到内置样例数据，保证演示不崩。

**数据迁移与回滚**：变更仅新增表，不改动既有字段；`init_db()` 使用 `CREATE TABLE IF NOT EXISTS`，可重复执行。
回滚步骤：`git revert <commit>`；如需清库，删除 `data/creatoros.db` 后重启即可（无历史数据依赖）。

### 5.3 第三轮（P2：账号体系与多设备同步）

| 项 | 实现 |
|---|---|
| 密码存储 | PBKDF2-HMAC-SHA256，20 万次迭代 + 16 字节随机盐，格式 `pbkdf2_sha256$iters$salt$hash`，不保存明文 |
| 会话 | 随机 256 位令牌；服务端只存 SHA-256 哈希；HttpOnly + SameSite=Lax Cookie，30 天有效；HTTPS 自动加 Secure |
| 数据隔离 | 登录用户 `owner=u_xxx`；未登录按设备 Cookie `dev_xxx` 隔离，共用浏览器不再是同一个匿名空间 |
| 新增接口 | `POST /api/auth/register`、`POST /api/auth/login`、`POST /api/auth/logout`、`GET /api/auth/me` |
| 防护 | 邮箱格式校验、密码 ≥ 8 位、登录/注册按邮箱限流 10 次 / 10 分钟 |
| 前端 | 侧边栏与顶栏头像打开「账号与多设备同步」弹窗，支持注册、登录、退出、状态展示 |

**数据库迁移与回滚**

- 迁移触发：`store.init_db()` 检测旧表缺少 `user_id` 时自动执行，仅执行一次。
- 迁移前自动备份：`data/creatoros.db.bak`。
- 变更方式：`comment_rules`、`saved_topics`、`imported_hits` 重建为 `(user_id, ...)` 复合主键；`drafts` 追加 `user_id` 列；新增 `users`、`sessions` 表。
- 回滚：停止服务 → 用 `data/creatoros.db.bak` 覆盖 `data/creatoros.db` → `git revert <commit>`。已登录账号会失效，但结构可完整还原。
- 旧匿名数据：保留在库中（`user_id=''`），迁移后不再展示，避免与新设备空间混淆。

**已验证（本地隔离库）**

- 注册 → `/auth/me` 返回用户；重复注册 409；错误密码 401；登录成功写入 `cos_session`。
- 两台客户端登录同一账号，收藏数据一致（多设备同步）；退出后回到各自设备空间，看不到他人数据。
- 匿名设备收藏写入 `dev_xxx`，登录账号看不到；评论规则同样隔离。

**已知限制**：账号体系暂未实现邮箱验证与密码找回（需接入 SMTP 服务）。

### 5.4 第四轮（P2：Render 持久磁盘）

- `render.yaml`：`plan: starter`（Render 的 Disk 不支持 Free 实例）、新增 `disk`（`creatoros-data`，挂载 `/var/data`，1GB）、环境变量 `CREATOROS_DB=/var/data/creatoros.db`、`CREATOROS_PERSISTENT=1`。
- 代码层：`store._connect()` 开启 SQLite WAL 与 `busy_timeout=5000`，降低多设备并发写锁冲突。
- 可观测：`GET /api/health` 增加 `db` 字段（`path`、`persistent`、`writable`、`users`、`saved_topics`、`journal_mode`），用于确认数据库确实落在持久盘。
- 验证：本地以 `/tmp` 目录模拟挂载盘，注册账号 → 收藏 → 重启进程 → 会话仍有效、收藏仍存在，`journal_mode=wal`。
- 回滚：在 Render 控制台移除 Disk、把实例改回 Free/移除 `CREATOROS_DB` 即可；数据库文件保留在 `/var/data/creatoros.db`。
- 注意：磁盘只能挂载到单个实例，因此服务需保持单实例运行，不能水平扩容。

### 5.5 第五轮（双模式存储）

- `store.py` 支持两种后端，业务代码零改动：
  - `DATABASE_URL=postgres://...` → Postgres（psycopg2）；
  - 未设置 → SQLite（路径 `CREATOROS_DB`）。
- SQL 写法统一：`INSERT ... ON CONFLICT ... DO UPDATE`、`INSERT ... RETURNING id`，两种数据库都支持（SQLite ≥3.35）。
- 兼容处理：`?` 占位符自动转 `%s`；Postgres 用 `RealDictCursor` 返回字典行；`_PgConn` 包装提交/回滚/关闭。
- 旧 SQLite 库的 `user_id` 迁移只在 SQLite 模式下执行；Postgres 首次启动直接建新表。
- `/api/health` 的 `db.backend` 标明 `sqlite` / `postgres`，Postgres 只暴露 `host/dbname`，不泄露密码。
- 实测：本地启动 PostgreSQL 16，注册 → 会话 → 收藏 → 规则 → 草稿 → 导入爆款全部通过；重启进程后会话与数据仍在；SQLite 模式同套用例回归通过。
- 切换方式：在部署平台加 `DATABASE_URL` 即切 Postgres，删掉即回 SQLite；两者都保留现有表结构与接口。

## 6. 已确认决策

1. SQLite 持久化 —— 已实施。
2. 热榜数据源 —— 手动导入 + 免费 RSS 聚合，已实施；付费 API（巨量算数、新榜）暂不接入。
3. 赛道自测、评论洞察、爆款推荐、草稿 —— 全部走真实 GLM，已实施；未配置 Key 或调用失败时自动回退 mock。
4. 账号体系 —— 邮箱 + 密码，SQLite 存储，可选登录（未登录按设备隔离），已实施。
